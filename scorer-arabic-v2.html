What makes a question scoreable

Before a writing prompt enters the AZE pipeline, it must carry four pieces of information. This tab explains what they are and what happens if any are missing. If your question has all four, head to Tab 2 — Create Question.

The four components

ComponentWhat it is
Task prompt The instruction the student sees. Written in Arabic, clear, and complete — no missing context, no ambiguous references.
Word range A minimum and maximum word count appropriate to the CEFR level being targeted. Drives the Word Count Compliance sub-metric.
Task requirements Four specific, named, discrete things the student must address. These are not the prompt itself — they are the structured checklist the annotator and scorer use.
Content quality descriptors For each of the four requirements, four band anchors (0–3) describing what absent, mentioned, developed, and extended look like in the student's response.

What happens if a component is missing

MissingConsequence
No task requirements Task Achievement and Content Quality dimensions cannot be scored — the pipeline has nothing to match the response against.
No band descriptors Content Quality dimension cannot be scored. The annotator cannot decide between 0, 1, 2, or 3 without anchors.
No word range The Word Count Compliance sub-metric defaults to N/A and drops out of the calculation.
Vague prompt Annotation quality degrades. The LLM cannot reliably identify evidence for requirements that aren't clearly stated.
What to do next. If your question already has all four components, go to Tab 2 — Create Question and load it in. Band descriptors are the most common gap — Tab 2 has a guided form for building them one band at a time.
Why this matters. V1 of the scorer would happily score a response against a vague prompt — and then confabulate justifications. V2's annotation-first design refuses to score anything it can't find evidence for. That means the question itself has to carry the evidence the scorer will look for.

What annotation is

The annotation pipeline marks up every piece of evidence in a student's response before any score is calculated. Each annotation points at a specific position in the text and labels what it is. Scores are then derived only from verified annotations — never from prose justifications.

Annotation runs in three stages: code first (cheap, deterministic), then LLM (near-deterministic, temperature 0), then a verifier that checks each annotation against the actual text. Anything that fails verification is dropped. What survives becomes the input to scoring. Annotations are immutable once verified — downstream stages read them, never rewrite them.

The rule. No annotation = no score contribution. A dimension cannot score itself out of thin air — it must point at evidence the verifier accepts.

Why annotations before scores

In V1, the AI was asked to score and justify in the same call. The justification was prose generated after the score had already been chosen. Nothing constrained the model to point at real evidence, and it would happily invent a quote that wasn't in the response. This is confabulation — convincing-sounding text that has no grounding.

V2 inverts this. The pipeline first asks the model: "Find evidence — quote the text, label it, mark its position." Only after annotations are produced and verified does scoring run. The scorer reads the verified annotations and does the arithmetic. It cannot make up evidence because it does not produce evidence — it only consumes it.

Practical effect. If the LLM hallucinates a quote, the verifier rejects it (the text isn't actually in the response). The dimension that quote would have supported loses that point of evidence. If a dimension has no surviving evidence, its score is nulled and a guardrail flag is raised.

What gets annotated

FamilyWhat it findsSource
word_count Total words in the response; in-range check against the task's word limit. Code
claim: Task requirements addressed by the response, and the specific sentence(s) where each is addressed. LLM
intelligibility: Sentences where meaning is unclear — broken syntax, missing referents, untranslatable fragments. LLM
cq: How well each task requirement is developed (0 absent · 1 mentioned · 2 developed · 3 extended). LLM
register: Dialect markers, MSA markers, and register lapses (informal phrasing where formal is expected). Code + LLM
range: Vocabulary variety, morphological range, sentence complexity. Code + LLM
cohesion: Arabic connectives (و، ثم، لكن، لذلك …) and coherence signals. Code + LLM
accuracy: Grammar errors — agreement, conjugation, dual form. LLM
orthography: Spelling errors — hamza, alif, taa marbuta, and general spelling. Code + LLM

Code vs LLM annotations

PropertyCode annotationsLLM annotations
Determinism Deterministic — same input always yields same output. Near-deterministic at temperature 0; rare variation remains.
Speed and cost Fast. No API call. No cost. Requires an API call per annotation prompt.
What it does Word count, spelling list lookups, connective scans, regex-matchable patterns. Requirement matching, grammar errors, dialect verb forms, intelligibility judgements.
Reproducibility Versioned lists (e.g. spelling_list_v3) — fully reproducible across runs. Model name + prompt version recorded on each annotation.
Reading this in context. Code annotations are the cheap floor that catches the obvious things. LLM annotations are the expensive ceiling that handles judgement. Several families use both — for example, orthography: uses a code-side spelling list and an LLM pass for errors the list doesn't cover. The verifier treats them identically once produced.

What the verifier checks

The verifier is the trust gate between annotation and scoring. Every annotation — code-source or LLM-source — passes through it, and only the ones that survive contribute to the score.

Verifier checkPurpose
Text span exists Prevent hallucinated quotes — the annotated text must be findable in the actual response.
score_in valid Prevent construct leakage — an annotation can only feed dimensions it is allowed to feed.
Overlap rules Prevent double-counting — the same evidence cannot score the same dimension twice.
Protected forms Suppress invalid penalties — certain word forms (e.g. canonical Quranic phrasing) cannot trigger error annotations.
Schema conformity Validate annotation structure — every field present, every type correct, every reference resolvable.
